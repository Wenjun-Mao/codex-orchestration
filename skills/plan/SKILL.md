# Save a Durable Project Plan

Use this skill when the director and user need to settle an outcome, scope,
tradeoffs, acceptance evidence, delegated authority, or an escalation boundary
before delivery. A project plan is the durable handoff between the director's
strategic decision and the coordinator's technical execution. It is not a
second workflow engine and it does not replace the execution DAG generated by
`codex-orchestration:coordinate`.

There is one approved project plan for the outcome, not three role-specific
plans that rewrite the same intent.

## Plan once, then bind the approved bytes

1. Follow the repository's existing planning location. If it has none, use
   `docs/plans/` and a descriptive dated Markdown filename.
2. Draft one plan containing the outcome, scope and non-goals, consequential
   decisions, checkpoints and dependencies, acceptance evidence, execution
   authority, and escalation conditions. Scale the detail to the work.
3. Mark the document `Draft` while it is being settled. After the director
   and user approve it, mark the exact revision `Approved` and bind approval to
   its exact content digest or immutable snapshot. A mutable path alone is not
   approval evidence.
4. Save and bind the approved plan before dispatch. Give the coordinator the
   authenticated approved bytes, or an immutable snapshot it can actually read
   in its worktree, together with the human-readable source path and digest.
5. Reuse content-addressing and atomic persistence already provided by Flow.
   Do not copy the execution DAG, create a second approval engine, or require a
   coordinator to rewrite the director's plan before starting work.

Native Plan mode and structured questions are optional host conveniences. In
ordinary mode this skill may write the planning document, but it does not
implement product changes. If native Plan mode prohibits writes, discuss the
plan there, then persist the exact approved revision after leaving that mode
and before dispatch.

## Ownership and revision rules

The director owns the user's goals, strategic tradeoffs, scope, exclusions,
acceptance, and delegated authority. The coordinator owns technical breakdown,
dependency ordering, executor selection, integration, verification, and
authorized release work. A coordinator may add implementation detail without
changing approved intent.

Routine technical refinements stay with the coordinator. A material change to
intent, acceptance, risk, scope, or external authority returns to the
director/user for a new approved revision. The old approval never silently
authorizes changed work. A bounded read-only planning question may precede
approval only when its question, evidence boundary, and follow-up are explicit.

## Handoff and completion boundary

For a director, “Implement the plan” means:

```text
persist and bind the approved plan -> dispatch one coordinator -> return once
```

Use the [assignment and result briefs](../../templates/references/assignment-and-reporting.md).
The coordinator's initial assignment must name one observable outcome, scope,
constraints, acceptance checks, and exactly one reporting recipient/path. It
must include the approved plan digest or immutable snapshot; a linked worktree
must not be expected to see an uncommitted director file.

After the bounded dispatch and any exact identity or acceptance check, the
director reports the dispatch state once and returns to strategic conversation.
It does not implement the plan locally, repeatedly call `wait_threads`, read
progress in a loop, or narrate delivery. A provisional creation result is
pending evidence, not proof of failure; preserve the one-shot operation and
return an honest pending state instead of retrying or entering a lookup loop.

The coordinator returns one complete result containing status, actual results,
verification evidence and artifact links, unresolved risks, and the next
decision if any. The director reviews that result against the approved plan;
transport or receipt delivery is not acceptance.
