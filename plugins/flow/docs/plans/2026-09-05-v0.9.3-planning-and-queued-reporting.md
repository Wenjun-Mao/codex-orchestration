# v0.9.3: durable planning and queued reporting

Status: **Approved for implementation on 2026-09-06.** The user approved direct execution after incorporating the staffing and same-host clarifications below. The release/install authority and acceptance gates in this plan apply; material pivots and necessary App trust/restart actions still require escalation.

## Outcome and scope

The director remains available for strategic discussion after delegating delivery. An approved plan is durable and reaches the coordinator intact. A delegated task writes its complete final report once; reporting machinery captures that final and queues it for its upstream task without interrupting active work.

The causal question is whether the present planning, dispatch, and reporting gaps can be closed with a small skill-level contract and a thin native-queue adapter, without another orchestration engine.

The cheapest safe direct attempt is one real, same-host director → coordinator assignment using a saved plan and the existing trusted Stop-hook/native-queue approach. Focused tests support that attempt; they are not a substitute for it. After the first implementation/test checkpoint, attempt the live path or stop and replan if unsafe. Further instrument-only expansion needs explicit authorization.

Target release: **v0.9.3**. This document plans the desired workflow manually once; implementing the planning skill must not require regenerating or reapproving this plan.

### Approved first-release boundary

Automatic reporting covers visible tasks whose sender and recipient are on the **same local Codex host**: the same machine's local Codex environment and native queue storage, not necessarily the same project or worktree. Different local projects still require an explicit authorized reporting relationship. A local director and SSH-hosted coordinator are cross-host even if they work on the same repository. Cross-host delivery is out of scope and retains an explicit manual path; it must not silently steer or use an unverified transport.

The user's `Codex_Usage main` observation illustrates the acceptance gap: a prompt successfully stopped director babysitting, but the coordinator's final did not arrive. New registered assignments must solve both halves together. This checkpoint does not promise retroactive delivery of finals from already-finished, unregistered tasks, and it does not authorize contacting that project.

Do not contact or change pilot projects. Do not read or edit `AGENTS.md`, install Superpowers, migrate prior journals, add model-availability probes, or alter running assignments implicitly.

## 1. Planning belongs with the director; delivery belongs with the coordinator

Add `codex-orchestration:plan`, routed from `index` and referenced by `direct` and `coordinate`.

The director and user settle the outcome, consequential choices, scope, exclusions, acceptance criteria, and delegated authority. The coordinator owns technical breakdown, dependency ordering, executor selection, integration, verification, and authorized release work. Executors choose local tactics within their assignments.

There is **one approved project plan**, not three mandatory layers of rewritten plans. A coordinator may add implementation detail without changing approved intent. A consequential uncertainty may justify bounded read-only planning assistance before approval.

### Durable plan contract

- Follow the project's existing planning location; otherwise use `docs/plans/` with a descriptive dated Markdown filename.
- Save the plan before dispatch. Mark drafts and approved revisions distinctly; bind approval to the exact content, not merely a mutable path.
- Include outcome, scope/non-goals, important decisions, checkpoints/dependencies, acceptance evidence, execution authority, and escalation conditions. Scale detail to the work; do not impose a large form on a small assignment.
- Supply the coordinator with authenticated approved bytes or an immutable snapshot it can actually read. An uncommitted file in the director checkout cannot be assumed to exist in a linked worktree.
- Reuse content-addressing and atomic persistence primitives for a thin assignment handoff. Preserve the human-readable source path for navigation. Do not duplicate the workflow DAG or invent a second approval engine.
- Routine technical refinements stay with the coordinator. Material changes to intent, acceptance, risk, or external authority return to the director/user; old approval must not silently authorize changed scope.

### Native Plan mode remains optional

Use native structured questions where available. The skill provides durable planning and role-aware handoff; it does not replace the App's question UI.

In ordinary mode, the planning skill may write planning documents but does not implement product changes. If native Plan mode prohibits writes, discuss there, then persist the exact approved plan after leaving that mode and before dispatch.

For a director, “Implement the plan” means **persist/bind the approved plan → dispatch a coordinator → return to the user**, not implement locally. This is a skill contract, not a claim that a plugin can reprogram the App button or sandbox every mistaken director action. Test realistic instructions that could otherwise pull the director into implementation.

## 2. Director dispatch-and-return

Make the ownership boundary explicit in the director skill and generated coordinator assignment:

- The director performs bounded dispatch and any necessary exact identity/acceptance check, reports the resulting dispatch state once, and ends its turn.
- It does not repeatedly call `wait_threads`, read progress, narrate implementation, or monitor unchanged state. Ending the turn does not mean the delegated business outcome is complete.
- A provisional creation response remains pending evidence, not proof of failure. Preserve the one-shot operation and return with an honest pending state instead of retrying creation or entering an open-ended lookup loop.
- The coordinator receives its real approved assignment in its initial prompt. Its first-turn acceptance binds its own identity and reporting route before substantive delegated work can finish. Reuse existing launch/identity patterns; do not restore a bootstrap-only waiting turn.
- Keep coordinator handoff distinct from executor contracts: a coordinator is allowed to orchestrate; an executor contract must not be relabeled to grant that authority accidentally.
- The coordinator owns executor waiting, progress management, technical recovery, verification, and delivery within scope. It escalates only a material decision, new authority, or a genuine blocker it cannot resolve within that authority.
- The director may inspect progress when the user asks or an actionable report warrants review. It does not cancel or interrupt children merely because it returns to strategic conversation.

A coordinator writes one complete final report containing result or blocker, evidence and artifact links, unresolved risks, and the next decision if any. The director reviews that result before accepting it; transport is not acceptance.

## 3. Ship final-output reporting through the native queue

Reuse the reviewed prototype and its real canary findings. Adapt it into the package rather than installing the trial as a dependency or creating another research project.

### Assignment and route binding

Register an exact upstream route for each delegated coordinator or visible executor before its work is armed. Bind sender/recipient task and host identities, assignment identity, and applicable run/runtime/recipient-generation authority. A sender has one active assignment/upstream route; project names and titles do not authenticate it.

The deterministic child acceptance can establish the ready sender identity if the App returns only a provisional or unknown result shape. Known host identities must agree. This closes the fast-completion race without a second assignment message or normal-path private history scan.

The root director has no upstream route merely because it is using Flow. Unrelated task finals are ignored. Native subagents retain their native parent-return behavior; this checkpoint does not build a second external reporting route for them.

Keep authoritative assignment/route evidence durable and repository-scoped. The hook may use a minimal host-local locator to reach an authenticated route, not a global coordination registry. Establish the supported locator/`PLUGIN_DATA` resolution during adapter implementation; do not assume that a CLI launched outside a hook receives hook-only environment variables.

### Capture and scheduling

- The task writes its full user-visible final once. The Stop hook captures that exact text and source turn identity; it must not ask the model to compose a second summary or duplicate the report into a separate file first.
- Capture final assistant output only. Never deliver `wait_threads` results, tool output, or interim commentary as the final report. An idle report can describe completion, a blocker, or a decision request; it is not automatically a success claim.
- Submit routine reports to the App's native queue. The App owns delivery scheduling: a recipient's active turn, including pending tools or `wait_threads`, must finish before the queued report starts a new turn.
- Do not add a recipient idle watcher, polling daemon, forced `queue/start`, task resume, or normal-path steer. Preserve the existing persisted urgent-interrupt path for rare genuine urgency.
- Preserve the full text and digest in a bounded envelope labeled as untrusted report data. Use explicit finite size/resource bounds; never silently truncate a report. Oversize or unsupported cases retain an inspectable report/failure and use the declared manual path.
- Verify the selected Stop event's semantics, including any continuation-hook interaction. Do not equate every hook invocation with irrevocable assignment completion or invent a general hook scheduler to compensate.

### One-shot delivery and truthful status

Persist capture and a one-shot attempt before queue submission. Deduplicate repeat Stop events using source assignment/task/turn, recipient binding, and final digest. A conflicting final for the same bound turn is an explicit conflict, not another silent delivery.

The native client message ID is a correlation key, **not a guaranteed server deduplication key**. Ambiguous submission is never retried automatically. Preserve an accepted queue ID even if a later diagnostic appears.

Expose minimal captured/submission/accepted-or-ambiguous evidence using existing persistence patterns. Queue acceptance is not recipient delivery. Do not mark a report delivered or reviewed just because `queue/add` succeeded, and do not continuously poll to manufacture that status.

Recipients review the complete report and relevant evidence. Reports do not replace terminal receipts, callback admission, disposition, integration, combined verification, or authorization. Keep ordinary executor callbacks quiet and fenced to their original authority; avoid a separately authored narrative callback duplicating the captured final.

The distinction is deliberate: a report explains the result; a receipt binds structured evidence to the exact assignment and outcome; acceptance judges whether the actual work satisfies the approved plan. Neither arriving prose nor a valid receipt alone establishes solution quality or authorizes cleanup. Coordinators and directors retain their delegated acceptance authority; this does not introduce routine user approval for every result.

### Adapter and runtime boundaries

Keep raw Stop payloads, native app-server commands, binary discovery, hook environment, and diagnostic parsing in the Codex App adapter. Core receives typed authenticated evidence; no App-private fields or current model names leak into governance.

Prefer the existing Node runtime for the packaged implementation, with the prototype's pipe/deadline tests ported alongside it. Use bounded nonblocking I/O and account for capture, startup, encoded payload/response size, and process cleanup in the budget.

The short-lived native queue producer is not globally read-only: it deliberately writes the native queue, and native app-server startup can have other side effects. Authenticate the supported binary and configuration, classify startup diagnostics, and never perform direct database edits or silent recovery/migration on the user's behalf.

Resolve hook entrypoint and reporter code into immutable package/runtime authority. Installing a new plugin must not hot-switch an active assignment's reporter contract. New automatic routes are opt-in through new supported assignments; do not invent reporting bindings for existing v0.9.2 runs.

Use supported plugin hook configuration and trust mechanisms. No hand edits to installed caches, trust records, or global configuration. Hook trust/reload remains a user action when required.

### Retirement and failure handling

Define route closure alongside assignment completion, archival, refresh, and unplug. Reject late or mismatched recipient-generation reports. A pending/ambiguous delivery cannot be silently erased by cleanup; expose it and require an explicit disposition before deleting its evidence.

Keep state out of temporary directories and immutable installed caches. Clean only exact checkpoint-owned resources. Do not parse or migrate arbitrary predecessor journals.

An unloaded, archived, interrupted, or unavailable recipient is not permission to load it, steer it, or substitute another task. State the supported native behavior and leave unsupported cases with bounded evidence and a manual recovery route. Crashes may require manual recovery; no exactly-once distributed-delivery framework is in scope.

## 4. Bounded implementation sequence

Delegate to one explicit **Sol-high coordinator**, with a rationale covering coupled role, adapter, and release decisions. Keep this director out of implementation and monitoring loops.

Default to **no more than three concurrent implementation lanes**. This is a coordination-cost budget, not a mandatory task count, lifetime task limit, permanent plugin rule, or research-established optimum. Use fewer when appropriate; the coordinator may adjust the staffing shape deliberately within scope, documenting why any higher concurrency is warranted without availability probing or silent escalation.

Three likely ownership areas are:

1. Planning skill, role instructions, concise plan/assignment template, and behavioral fixtures.
2. Thin approved-assignment/route binding and integration with existing lifecycle/runtime boundaries.
3. Stop/native-queue adapter, ported transport tests, hook packaging, and adapter evidence.

The coordinator chooses surface first and then the least-capable-sufficient model/effort for each actual slice, disclosing exact selectors and a rationale. Under the agreed policy, **Luna-xhigh** is appropriate to consider for well-scoped mechanical documentation or fixture work; **Terra-high** for bounded nontrivial implementation/review; and **Terra-xhigh** for difficult multi-module lifecycle or transport work. These are recommendations, not Terra-only assignments. A deliberate override requires a replacement rationale.

The coordinator chooses non-overlapping ownership and serializes shared interfaces/integration. It may collapse or subdivide the areas if that is cheaper and simpler. All native calls use explicit selectors and bounded context; no inherited or automatic escalation.

Record one concise ADR extending ADR 0048 with approved planning, dispatch-and-return, and report transport boundaries. Update architecture, mission, relevant skills, compatibility register, and lessons learned only where the contract changes. Do not add unused validators or role schemas solely to make tests pass.

## 5. Verification and live acceptance

### Focused automated gates

- Saved-plan approval/content binding; mutation after approval; a linked worktree cannot see an uncommitted plan; coordinator still receives exact approved content.
- Realistic fresh-director “plan” and “Implement the plan” inputs route correctly, without local implementation or waiting loops. Existing waiting remains valid for coordinators.
- Sender acceptance before/after App creation result, provisional result, rapid final, duplicate title/project, wrong sender/recipient/generation, and no duplicate creation.
- Complete Unicode/multiline final, near-limit and oversize payloads, duplicate/conflicting Stop, no-route root director, tool/commentary/wait exclusion, and continuation-hook semantics.
- Real child-process partial lines, timeout/EOF, response-size limits, process cleanup, version/configuration rejection, startup anomalies, and accepted acknowledgment followed by error. Preserve the prototype's regression for buffered `readline` blocking despite readiness checks.
- Route/capture/attempt persistence across restart; no automatic replay after ambiguity; runtime pinning across plugin replacement; late report fencing; pending-report cleanup rules.
- Dependency direction and package/runtime parity, including hooks and required scripts; no trial hardcoded IDs/paths, hidden trust edits, direct SQLite writes, new legacy mutators, or `AGENTS.md` authority.

Run the established full Node suite, source/schema checks, package dry run, plugin and all-skill validation, release identity checks, and `git diff --check`. Source-text tests alone do not prove director behavior or native scheduling.

### Live RC gate on the current App

The historical successful hook canary used **codex-cli 0.153.1**. The bundled CLI observed on 2026-09-05 is **0.153.4**; the trial's exact-version guard would reject it. Revalidate on the current App, with any fix classified at its originating layer. Do not simply loosen the guard or claim the old canary proves the current build.

Use checkpoint-owned same-host tasks and a bounded assignment:

1. Save and approve a small plan; dispatch a real coordinator with exact plan bytes and an upstream route. Confirm the director returns without waiting and can continue a strategic conversation.
2. Run useful bounded work, including a visible executor → coordinator report. Confirm the executor's first turn is its real assignment, not a bootstrap acknowledgment.
3. Exercise a recipient busy in an ordinary turn and, separately, one pending a real `wait_threads` call. No report is delivered until that turn ends; no wait/tool output is captured as the report.
4. Confirm the actual installed Stop hook submits the complete final—not a manually invoked replacement producer—and that native delivery preserves source/turn identity and exact text/digest. Distinguish submission acknowledgment from a recipient's actual incoming review turn.
5. Exercise the real coordinator → this long-lived director route. No separately authored callback summary or manual retrieval should be necessary to read the complete report. The director still reviews supporting artifacts before acceptance.
6. Check deduplication and an explicit unsupported/ambiguous case without retry or steering. Observe process exit and retained evidence.
7. Repeat any failed App-facing segment after its root-cause correction and regression. A failed essential segment blocks stable promotion.

Use forward behavioral tests without revealing the intended answer to the tested director. If a native UI approval interaction cannot be faithfully automated, ask the user to perform that bounded interaction rather than claiming a substitute tested the button.

After all gates pass, promote, annotate/tag, push, build and install immutable **v0.9.3** using the existing release process. Prove artifact/cache equality and authenticate the installed skills, hook definition, reporter authority, and actual same-director report delivery after required reload/trust.

Retire the trial plugin only after its replacement is trusted and verified, with exact scope and recovery evidence. Archive and remove only this checkpoint's eligible canary tasks/worktrees/branches using an exact cleanup plan. Preserve concise durable release evidence; no pilot cleanup or arbitrary historical deletion.

Completion means: a durable approved plan reaches a coordinator; the director returns to discussion; full final reports arrive through the non-interrupting queue on the supported host; Flow's result/acceptance safeguards remain intact; and the exact released installation passes those checks. It does not mean cross-host reporting or all future App versions are proven.
