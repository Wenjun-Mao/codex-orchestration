# v0.9.7 RC7 runtime-bundle report-staging failure

Date: 2026-09-07

## Failure

After the authenticated v0.9.6 to RC7 refresh, coordinator report-route
registration was invoked through the exact pinned RC7 runtime. Assignment,
iteration, and route records persisted, but locator installation failed with
`ENOENT` for the pinned runtime's `package.json`. Retrying through the matching
installed package then failed with `Existing iteration conflicts with assignment
authority`.

No report was captured or submitted, and no ambiguous native host call occurred.

## Root cause

The staged reporter manifest deliberately includes `package.json`, but runtime
bundle acquisition copied only executable and instruction directories. Tests
registered routes from a package checkout, so they did not exercise the pinned
runtime entrypoint used by live coordination.

The first local failure also exposed a retry defect: iteration creation compared
the entire regenerated record, including fresh timestamps, with the already
persisted iteration. A deterministic partial registration therefore could not
resume even though its assignment identities matched exactly.

## Durable correction

- Include `package.json` in every authenticated execution-runtime bundle.
- Treat assignment iteration creation as idempotent when its immutable director
  and coordinator member identities match, while preserving the persisted
  iteration and any later lifecycle progress.
- Register a coordinator route through the pinned runtime in CLI coverage and
  replay coordinator registration after time advances in assignment coverage.

For this live RC7 transition only, the missing locator step was completed by
calling RC7's exact `installRepositoryReportLocator` operation against the
persisted route. This did not edit state directly, reinstall the launcher,
capture a final, or replay a native submission. The resulting staged runtime
was verified against its content-addressed manifest before work resumed.
