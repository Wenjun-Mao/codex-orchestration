## 1. Strongest counterexample: a cancelled assignment disappears from continuation authorization

**Classification: source-confirmed lookup/ordering defect; the composed public-operation sequence below is not executed.**

### Minimal sequence

Use a coordinator-only assignment, avoiding executor-cleanup complications:

```text
Assignment A is open; source execution S has unfinished work.
    → prepare semantic refresh H: S → T
    → apply H; S is terminal and its execution retirement is recorded
    → director cancels A
    → invoke the exact target activation with --refresh-id H
```

Compare two histories at the last step:

| History                | Assignment state                                         | Appropriate decision                                                                       |
| ---------------------- | -------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| Safe continuation      | A remains open; S is its latest authenticated execution. | Permit the exact continuation, subject to the other checks.                                |
| Withdrawn continuation | The director has cancelled A after source retirement.    | Do not silently admit T as an unassigned continuation. Preserve H for explicit resolution. |

The **source namespace, source terminal record, replacement semantics, and handoff can be identical** in these histories. The distinguishing fact is outside that namespace: assignment cancellation.

### Exact source chain

`prepareRefresh` checks that an identified assignment is `open` when replacement work is required. That is a preparation-time check, not continuing authorization. See **`lib/compat/refresh.mjs:1265–1370`**.

After source retirement, `retainRefreshAssignmentRetirement` records the execution as `resource_disposition: "refresh-retired"` in shared assignment authority. This preserves an execution’s retirement without retiring the assignment itself. See **`lib/compat/refresh.mjs:1540–1590`**.

`cancelAssignmentResult` allows an open assignment to be cancelled after its bound executions are terminal, provided the applicable report/iteration checks pass. It closes reporting and cancels the iteration while deliberately retaining coordinator/Git ownership. Neither this function nor its public CLI dispatch checks for a pending refresh handoff. See **`lib/assignment-acceptance.mjs:179–325`** and **`bin/codex-flow.mjs:1505–1615`**.

Then:

* `assignmentForExecutionRetirement` searches only `registering`, `open`, and `accepted`.
* `openAssignmentForSender` searches only `registering` and `open`.
* `bindAssignmentRefreshExecution` returns `status: "no-open-assignment"` when that second lookup returns null.
* `consumeRefreshActivation` calls `prepare()` and `admit()` **before** `bindAssignmentRefreshExecution`, and does not reject that returned status before consumption proceeds.

See **`lib/assignment-authority.mjs:560–610, 750–865`** and **`lib/compat/refresh.mjs:2080–2225`**.

**The predicted outcome is target admission without the original assignment binding.** In the coordinator-only case, cancellation changes shared assignment/reporting/iteration records rather than the source namespace tree authenticated by the handoff.

### Does existing evidence distinguish the histories?

**Yes.** The assignment still exists and retains its exact `execution_bindings`, state, and cancellation evidence. The problem is not missing evidence; it is filtering out the evidence before deciding whether execution was assignment-backed.

This is the state-filtered version of your approved rule:

> **“No open assignment found” does not establish “this execution was standalone.”**

### Smallest correction and decisive test

Resolve the exact source execution’s assignment association **across terminal as well as open states**, then apply continuation permission separately. Before target preparation, require that an assignment-backed replacement remains an authorized continuation of that exact assignment and source binding. Do not fall back to standalone execution when the association exists but permission has ended.

The eligibility check must also remain stable against assignment cancellation. The repository admission lock alone does not establish that: assignment updates use their own assignment lock. Use the existing owner/lock protocol to serialize the relevant decision; an additional unlocked precheck would fix the sequential example but leave its concurrent counterpart.

**Test delta:** extend the existing test **“assignment-lived reporting binds the exact target before refresh source deletion.”** It already exercises semantic refresh, assignment binding, replay, and cancellation **after target activation**. Add the alternate ordering: cancel **after source retirement but before target activation**. Require either an explicit refusal of cancellation under the pending-handoff policy, or rejection of subsequent activation **before target preparation**—never successful unbound replacement. Keep the open-assignment continuation as the positive control.

Your approved retained-obligation and pending-handoff cases cover the ingredients. This particular **ordering and filtered lookup** is the additional assertion.

## 2. Refresh-ID admission can miss a changed, unrelated retained namespace

**Classification: source-confirmed validation-scope difference; fault-injection sequence not executed.**

### Minimal sequence

Start with two predecessor namespaces:

```text
P: authenticated, fully retired history
S: an open assignment whose execution needs semantic refresh

Prepare and apply H: S → T.
Then remove a required accepted-report record belonging only to P.
Activate T with the exact --refresh-id H.
```

Removing that record is a **negative-test mutation**, not a proposed recovery operation. It leaves S’s namespace, H, and the target Git baseline unchanged.

The safe history still authenticates P. The unsafe history cannot authenticate P’s claimed settlement. A valid handoff for S should authorize handling S’s particular outstanding work; it should not waive unrelated repository-history checks.

### Exact source chain

`prepareRefresh` loads its explicitly named source and calls `assertOtherRefreshSourceRunsSafe(source)`. That helper operates over runs in **that source’s lifecycle**, not other namespaces.

The ordinary activation branch invokes `assertFreshStartPredecessors` under the repository lock. The refresh-ID branch instead delegates to `consumeRefreshActivation`. See **`bin/codex-flow.mjs:650–790`**.

`consumeRefreshActivation` revalidates H, the target baseline, the named source’s cleanup, and the named source’s final tree before admission. It does not run repository-wide settlement classification for unrelated retained namespaces. The downstream admission function checks foreign **active** runs; that sentinel is not a substitute for authenticating an inactive namespace’s settlement evidence. See **`lib/compat/refresh.mjs:2080–2165`**, **`lib/run-lifecycle.mjs:625–760`**, and `lib/foreign-active-run-sentinel.mjs`.

There is a baseline-supported way to instantiate P: the special retired v0.9.7 predecessor. Its existing recovery test establishes that removing its accepted report blocks ordinary fresh activation. The refresh consumption path does not perform that same unrelated-predecessor check.

### Does existing evidence distinguish the histories?

**Yes.** P’s exact assignment-to-report relationship already expresses which record must authenticate. No additional certificate is needed.

The distinction is **validation scope**, not evidence format:

```text
exact handoff authority for S
    ≠
blanket admission permission in a repository also containing P
```

### Smallest correction and decisive test

Use shared historical facts at **first target admission through a refresh ID**, not only ordinary fresh admission. Apply operation-specific permission: the handoff can account for its exact source and authorized obligations, while unrelated retained namespaces still have to satisfy their applicable historical checks.

Do **not** simply call an ordinary “everything must be fully retired” guard. That would incorrectly reject the open assignment undergoing semantic refresh. Also distinguish new admission from replay that merely finishes an already-admitted target’s bookkeeping.

**Test delta:** combine an existing semantic-refresh fixture with one retained historical namespace. Leave the historical namespace intact for the positive case; remove one required record after H is prepared/applied for the negative case. Assert rejection before target preparation, with H preserved.

Your approved verification already includes multiple retained namespaces, missing evidence, and inspection-to-activation changes. **This may already be covered if those cases explicitly include `run activate --refresh-id` and an unrelated namespace.** A successful ordinary three-generation journey alone does not establish that cross-product.

## 3. Rechecking history under the lock does not refresh the target’s pre-lock Git snapshot

**Classification: source-confirmed ordering gap; proposed interleaving not executed.**

This is a live-admission issue immediately adjacent to historical eligibility, not a claim that the historical records are ambiguous.

### Minimal interleaving

Use a new linked coordinator checkout T, separate from the primary that preserves predecessor results:

```text
Ordinary activation snapshots T as clean at commit C.
    → asynchronous package/lifecycle work
    → another process modifies T
    → activation acquires the repository lock
    → historical settlement still authenticates against primary
    → activation persists/adopts the runtime built from the earlier snapshot
```

The predecessor evidence is identical in both histories. In the safe history, T still matches the clean captured baseline. In the unsafe history, T is now dirty or identifies a different branch/revision.

This does **not** require the repository lock to wait. The change can occur during the asynchronous work between the initial snapshot and lock acquisition.

### Exact source chain

In **`bin/codex-flow.mjs:605–650`**, ordinary activation calls `gitSnapshot(process.cwd())`, checks cleanliness, and builds the runtime from that captured repository identity before entering the later repository-lock section.

The locked ordinary branch authenticates predecessors, prepares target state, and admits it without resnapshotting T. `acquireRuntimeContext` validates and persists the supplied content-addressed context and bundle; it does not authenticate current Git state. `admitRunWhileRepositoryLocked` likewise does not repeat the live checkout snapshot.

By contrast, refresh consumption explicitly takes a target baseline snapshot inside its locked operation and checks it against the prepared handoff. That is a useful existing pattern, although it is not a guarantee against arbitrary external Git writes afterward.

### Does existing evidence distinguish the histories?

The runtime records the **expected** root, common directory, branch, and revision. The distinguishing fact is a **fresh live observation** that those still match and that the checkout remains clean. No historical record should be invented to represent that observation.

### Smallest correction and decisive test

Reauthenticate the target checkout at the locked, pre-preparation admission boundary and compare it with the context about to become immutable. On drift, fail before creating target authority; do not silently rewrite the already-derived runtime identity.

**Test delta:** add a deterministic synchronization point after the initial snapshot and before locked target preparation. Make a real change in T, leaving primary and predecessor records untouched. Assert rejection and no new runtime/workflow/run authority. This is synchronization of a real-Git test, not a fake Git implementation.

Your approved between-inspection-and-activation negative is related but not equivalent: a fresh activation process would normally see that earlier change in its initial snapshot. This case occurs **inside one activation invocation**.

## What these findings do—and do not—establish

**I found no intrinsic evidence-format ambiguity requiring a new registry for these three cases.** The relevant distinguishing facts already exist either in assignment authority, other retained namespaces, or live Git state. The failure risk is omitting them, filtering them away, or observing them at the wrong boundary.

I also found no additional concrete incompatibility that requires expanding the frozen-producer → candidate → later-consumer design. Your approved journey already targets the original selected-checkout lifetime problem and accumulation of retained namespaces. It should remain the main positive regression, not be replaced by a larger audit.

The open-assignment distinction is particularly important to preserve. Existing execution-retirement records explicitly distinguish `released`, `retained`, and `refresh-retired`; the existing refresh test demonstrates an assignment remaining open after an earlier execution has been refresh-retired. Requiring full assignment retirement for every historical execution would break that legitimate continuation.

### Priority

**Address the cancellation-before-consumption sequence first.** It is the strongest example because it uses an authorized lifecycle transition rather than corrupted evidence or a concurrent Git modification.

Then confirm that the shared classifier covers **unrelated namespaces at refresh-ID admission**, and that locked ordinary admission checks **current target Git state**, not just historical settlement. These are three narrow permission/ordering assertions—not a reason to reopen the architecture.
