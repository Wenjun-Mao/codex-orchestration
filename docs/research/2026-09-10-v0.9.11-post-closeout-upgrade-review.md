# v0.9.11 post-closeout upgrade: consultation evidence

Status: confirmed live failure; diagnosis reviewed locally; no correction approved
or implemented in this note. This is a sanitized account of local evidence, not
a replacement for the underlying Flow records or independent release acceptance.

## Source and decision

Released source: `6292c7fcb25744417590ce955dc7388bc9726a46`, immutable tag
`v0.9.11`. This note changes documentation only.

Question: what is the smallest durable architecture and test correction that
makes successful closeout compose with upgrade and subsequent admission, without
another caller-specific exception or weakening live ownership checks?

## What passed, and what did not

The fresh RC4 mixed canary completed coordinator-local A, an executor consuming
the exact committed A bytes to produce B, integration, verification, one native
executor archive, reclamation, normal run closure, director acceptance, and
coordinator archival/reclamation. An independently assigned useful successor
then verified the committed A/B results and completed its own normal closure,
acceptance, and reclamation. Original provisional creation evidence remained
intact when executor start preceded coordinator reconciliation.

Both runs were closed with zero unresolved fences and terminal-ready audits.
Both results were preserved on disposable main at
`1fa9d86cd8803231cc79c030ee0cdbc84c6ca2fd`. Only the primary checkout remained;
both coordinator worktrees and disposable branches were gone. Assignment routes
and locators were retired. The RC4 namespace remained as historical evidence.

After installing and reloading stable v0.9.11, the exact stable CLI's
`refresh inspect --invoking-skill <loaded-stable-refresh-skill> --json`, run
from the surviving primary, authenticated stable authority but returned:

```text
route: blocked
reason: Refresh source repository authentication: spawnSync git ENOENT
mutation_performed: false
```

Stable had no namespace yet. RC4 had no active run and two closed runs. The newer
selected predecessor was `v0911-rc4-successor-verification`; its recorded
coordinator checkout had been legitimately reclaimed. Git worked in primary;
both ordinary and absolute Git executable invocations failed with that removed
checkout as cwd. This is not evidence of an App-update or executable PATH defect.

The previously completed delivery/successor gates remain valid. They did not
prove the later RC4-to-stable upgrade boundary. No historical-state rewrite,
worktree recreation, repair install, or unplug was used to hide this failure.

## Source-backed diagnosis

- `lib/compat/refresh.mjs`: `inspectRefresh` selects an active run or the newest
  terminal run, then calls `loadRefreshSourceAuthority` before
  `assertOtherRefreshSourceRunsSafe`.
- `lib/compat/refresh-source.mjs`: `locateRefreshSourceSnapshot` checks the
  content-addressed context, then invokes Git from its recorded repository root
  before loading the remaining bundle/exporter authority.
- That module already has `assertReclaimedClosedRunSettled`, used by
  `assertOtherRefreshSourceRunsSafe` for missing **non-selected** closed runs.
  The selected loader fails before this path is reached.
- `test/refresh-v09.test.mjs`, test named “v0.9 refresh recognizes a reclaimed
  closed predecessor only through its authenticated terminal audit”, removes
  an older run's checkout but creates the newer selected closed run in the
  surviving primary. It does not cover the actual post-cleanup topology.

Thus the observed failure and the test coverage gap are confirmed. The best
fix location and sufficiency of existing terminal evidence still need review.

## Candidate direction, not a decided implementation

Consider one shared classification of live authority versus immutably settled
terminal authority, applied consistently to selected and other runs. Inspect,
refresh preparation, and actual fresh admission must agree; making inspection
say `fresh` while activation still rejects the namespace would not solve it.

Challenge this proposal. In particular, determine whether existing terminal
evidence is sufficient, whether a simpler ownership boundary is possible, and
whether this is another symptom of duplicated lifecycle interpretation.
Keep live and abandoned/unresolved cases fail-closed. Do not introduce a new
registry, migration engine, synthesized evidence, or rebind merely to avoid a
missing-directory exception.

The decisive regression should compose real public operations: complete and
accept work, reclaim all relevant coordinator checkouts, inspect under the next
runtime, and actually admit useful successor work. Add only the distinct
negative cases needed to protect that boundary. Avoid duplicating full suites.
