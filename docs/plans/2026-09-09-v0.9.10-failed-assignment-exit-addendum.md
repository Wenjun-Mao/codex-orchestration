# v0.9.10 addendum — explicit failed-assignment exit

Status: Approved — user authorized the minimal cancellation operation after
review of the missing failure-exit path. This extends the preservation-owner
addendum; it does not accept RC2 or waive the fresh live release gate.

## Outcome and boundary

Make an unsuccessful assignment terminal without calling its result accepted.
Reuse the existing `cancelled` assignment state and reporting retirement
mechanisms. Do not add a new registry, recovery subsystem, generic historical
reader, forced cleanup mode or success receipt.

The current run may be abandoned through its original snapshot, but the shared
assignment and report route outlive that run. The public workflow currently has
only successful acceptance/retirement, despite its schema admitting cancellation.
Fix that assignment-lifetime boundary rather than weakening run or Git checks.

## Minimal contract

Expose director-authorized assignment cancellation for an exact assignment,
with a concise reason and durable attribution. Use existing authority/state
records; add only fields essential for an auditable cancellation if absent.
Reject caller/recipient mismatch and conflicting previously accepted/retired
outcomes. Define repeat semantics so the same completed cancellation is safe
to inspect/resume without duplicating actions or silently changing its reason.

Cancellation is not abandonment of a still-running task, host archival, Git
reclamation, successful iteration closeout or release acceptance. Require fresh
evidence that no owned execution is active before terminalizing the assignment;
for RC2, use its original runtime's abandonment and existing terminal child
evidence. Do not infer inactivity merely from an idle UI task.

Retire the exact reporting route/locator through their existing operations,
preserving accepted delivery records as messages rather than success evidence.
Define interruption/retry ordering within existing locking/revalidation so a
partially completed cancellation can finish without reopening execution or
accepting late reports. Do not rewrite original run/receipt/archive outcomes.

Make remaining resources explicit: the retained coordinator worktree and
delivery branch still contain release work and must not be archived or deleted
by cancellation. An iteration may retain unresolved physical closeout, but it
must not masquerade as an active assignment or a successfully closed iteration.
Prove whether the same sender and retained worktree can be admitted under a
new assignment without overlapping cleanup authority. If this needs a new
ownership-transfer framework, stop and return the exact conflict.

## Proof before live recovery

Use focused existing fixtures to exercise the real command chain, including:

- Rejection while an owned run/child is active, and rejection of wrong director.
- Failed terminal run with completed archived children → cancellation → exact
  route/locator retirement, with coordinator code/resources preserved.
- Safe retry after interrupted cancellation; late-report rejection; no false
  result acceptance or host-action replay.
- Original-snapshot abandonment → cancellation → existing refresh → fresh
  assignment/run admission for the same coordinator and newer candidate.

Use separate source/target package namespaces in this last proof, not a
same-version library fixture labelled cross-version. Verify final state across
run, assignment, iteration, route and locator; stopping after the first command
is not sufficient. No full-suite rerun for each edit or new harness framework.

## Authorized RC2 sequence and release

After the complete isolated proof passes, authenticate current live state and
perform only the exact failed RC2 disposition: original-runtime abandonment,
new director cancellation, existing bounded refresh and new-run admission in
the proven order. The director executes the director-owned cancellation; the
coordinator supplies its exact request and evidence. Preserve failed RC2
evidence outside any namespace the approved refresh removes. Never replay the
completed executor archive or re-delete its already removed branch.

Keep the existing release coordinator and delivery branch. Freeze its checkout
during the new canary run; code corrections must not silently alter a no-change
run's admitted baseline. Complete the preservation addendum's fresh mutating
executor integration/closeout gate before stable promotion. Required final
tests, artifact/cache identity, App reload and director acceptance remain.

Update one concise durable decision and the stage-connection audit's failure
exit finding. Preserve this addendum in the delivery branch. No pilot contact,
AGENTS.md access, unrelated cleanup or primary movement. If the bounded chain
reveals another unrelated authority gap, pause before further expansion.
