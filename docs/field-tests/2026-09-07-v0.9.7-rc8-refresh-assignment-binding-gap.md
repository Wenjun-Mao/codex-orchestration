# RC8 refresh omitted the assignment execution binding

## Failure

The live RC8 refresh inspection was ready to replace the active RC7 execution,
but the assignment authority still contained only the RC7 run binding. Consuming
that handoff would admit RC8 and remove RC7 without adding the replacement run to
`execution_bindings`.

The first hermetic attempt used unpublished RC8 as the source and found that
its own exporter rejected the root-level `package.json` RC8 had added to runtime
bundles. Inventory across configured local projects found no retained RC8
execution, and the real assignment remained on RC7. No RC8-only compatibility
capsule was admitted to stable authority. The release regression instead uses
the exact live-shaped RC7 source; current source bootstrap code accepts exactly
`package.json` for current and future bundles.

## Root cause

`consumeRefreshActivation` authenticated and persisted the replacement runtime,
workflow journal, run admission, refresh origin, and consumed handoff, but never
joined the admitted run to the assignment-lived authority. Assignment-aware
commands filter by those bindings, so durable report transport could continue
through the assignment locator while target-run command authority silently
diverged.

The locator was not the failing layer. It already points to shared assignment
state and pins a content-addressed reporter runtime outside the removable run
namespace.

## Durable correction

Refresh consumption must append the exact target execution binding to the same
open assignment under its existing lock. The append occurs after target admission
and origin persistence, but before the handoff is marked consumed or the source
namespace is removed. Exact replay is idempotent; a changed target binding or a
transition that does not extend the latest authenticated source is rejected.

Regression coverage exercises binding replay, binding conflict, and interruption
after the binding write followed by ordinary refresh resumption.

## RC10 live gate exposed the missed coordinator shape

The first real RC7-to-RC10 `refresh prepare` failed before writing handoff state:
`Refresh decisions must cover every visible executor task exactly once`. The
source workflow had one genuine `execution_kind: coordinator` task with a
started `coordinator-work` record. Decision normalization selected only
`task-thread` tasks, so it rejected the coordinator decision. Omitting that
decision would have selected the no-replacement clean-start path and bypassed
target activation and assignment rebinding.

The regression had been named “direct coordinator” but its generated contract
still used the fixture default `execution_kind: task-thread` and never exercised
`workflow local start`. That fixture shape masked the contract gap.

The correction makes unfinished coordinator claims refresh-managed and permits
only discard-and-reissue for them. Replacement evidence retains the exact
local-work operation ID, while cleanup remains empty because coordinator work
owns no child task, App archive, worktree, or executor branch. Completed
coordinator claims are excluded from reissue, as are integrated and accepted
no-change dependencies; an empty decision set is reserved for a true no-work
clean start. Exact RC7-source tests now execute CLI activation, coordinator-work
start, prepare, apply, target activation, assignment binding interruption, and
replay. A separate completed coordinator-work test proves the clean-start
distinction.
